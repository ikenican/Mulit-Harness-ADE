Shared Project Memory

一份 Git 版控的專案記憶，讓 Claude Code、Codex、Antigravity 三個 agent 開局自動載入 —— 換電腦或換 agent 都不必重新解釋專案、重新掃描程式碼。

v1.1.0：本圖的「記憶 commit／push 進專案 repo、post-merge」已不再適用。記憶只在 clone 本機，跨電腦共用改由 Agent Workbench：設定 → 記憶同步（私人 GitHub repo／OneDrive／Google Drive）。現行規則見 README「Storage」一節。

01

Business Context

這不是知識庫，是交接棒。目標是消除「換環境就要重講一遍」的重複成本。

Objectives

  • 跨機延續 — 換電腦後 agent 立即知道進度與下一步
  • 跨工具延續 — 三個 agent 共用同一份事實來源
  • 零手動儀式 — 不必貼開場白、不必記得更新記憶
  • 可審查 — 記憶跟著程式碼一起 commit 與 review

Users & Value

  • 主要使用者 — 在多台電腦、多個 agent 之間切換的個人開發者
  • 痛點 — 每次切換都要重述架構、重掃 repo、重做已完成的工作
  • 價值 — 用約 1,000 tokens 的開局成本，換掉 10k–50k 的重複探索
  • 邊界 — 不取代 git 歷史、不取代文件；只保留「下一步所需的最少可靠資訊」

Data Flow

Sources → Processing → Outputs。記憶檔是資料來源，腳本與 git hook 是處理層，三個 agent 的 context 是輸出。

Processing Pipeline

一個 session 的四個階段。點選任一階段，在下方系統圖中追蹤它實際走的路徑。

04

System Architecture

五個分層，由下而上：資料在最底層，往上經過處理層與進入點，最後抵達 agent。Git 層橫跨在旁強制執行。四個階段對應 §03 的管線，選一個即可追蹤它實際流經的路徑。

為什麼 col 2、3 在開局時沒有連到資料層？ 因為那時不需要 —— handoff 早在上一次收工由 sync-entry-files.sh 生成進它們的 entry 檔了。Claude Code 走「執行腳本」路徑，另外兩者走「靜態檔案」路徑，這正是本設計的核心取捨。
05

Features

功能性需求（做什麼）與非功能性需求（做得多可靠）。最後一列是這套設計誠實的地板。

Functional

  • 自動載入 — 開局取得 tier-1 記憶，無需人工提示
  • 分層讀取 — tier 2 按需，完整內容常駐磁碟
  • 更新門檻 — 唯讀／瑣碎工作不寫檔
  • 自動提交 — agent 自行 commit 記憶（pathspec 限定）
  • 安全同步 — ff-only ＋三重守衛
  • 一鍵安裝 — /memory-init 或 install.sh，冪等不覆蓋

Non-functional

  • 可攜性 — Windows／Git Bash 與 Linux／busybox 皆實測通過
  • 安全性 — secret 只掃新增行；移除舊金鑰不誤擋
  • 不破壞性 — 從不 force-push、rebase、reset；不碰使用者的碼
  • 可逆性 — 記憶 commit 可 git reset --soft HEAD~1
  • 低成本 — 約 1,000 tokens／session，佔 5 小時視窗 <1%
  • 優雅降級 — 無 remote 時除跨機外全部照常運作

06

Deployment

單一必要條件是本機 git init。remote 只有跨機才需要，且不限 GitHub。

Prerequisites

  • 必要 — git、bash（Windows 用 Git Bash）、本機 git init
  • 選用 — 任何 git remote（跨機才需要）
  • 每台電腦一次 — git config core.hooksPath .githooks
  • 環境變數 — MEM_AUTOSYNC=1（拉）、MEM_AUTOPUSH=1（推）

Install workflows

  • Claude Code — /memory-init
  • Codex／Antigravity／手動 — bash install.sh [repo]
  • Windows — .\install.ps1
  • 兩條路徑共用同一支 init-memory.sh，冪等、不覆蓋既有檔案

Sync model — 只有一種正確形狀

DON'T 整個 repo 放進雲端同步資料夾

  • 順序無保證 — ref 可能先於它指向的 object 抵達 → bad object
  • 沒有 merge — 雲端挑一個贏家，另一台的 commit 無聲消失
  • Files On-Demand — git 讀到佔位符會卡住

DO 雲端只放 bare repo 當 remote

  • 只在 push／fetch 時寫入 — 短暫離散，雲端有時間收斂
  • 真正的衝突偵測 — 非 fast-forward 直接拒絕
  • 對 git 只是路徑 — GitHub／NAS／OneDrive／Google Drive 行為一致
# 第一台，一次
git init --bare "D:/OneDrive/git-remotes/myproj.git"
cd /d/repos/myproj                          # 工作區在雲端資料夾「外」
git remote add origin "D:/OneDrive/git-remotes/myproj.git"
git push -u origin HEAD

# 其他每一台
git clone "D:/OneDrive/git-remotes/myproj.git" D:/repos/myproj
git config core.hooksPath .githooks         # 每個 clone 都要；commit .githooks/ 不會自動生效
