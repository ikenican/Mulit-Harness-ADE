桌面程式、遠端橋接、手機程式：三個執行環境，同一組終端

Electron 桌面程式擁有 CLI 子行程；跑在它主行程裡的區網橋接把同一組終端用 HTTPS 再發佈一次； iPhone 的主畫面網頁 App 接上去。Cowork 在主行程協調會議與核准後的工作；模型執行仍由官方 CLI 負責。

官方 CLI 負責 agent runtime。工作台提供編輯、Git、終端、共享記憶與 Cowork 協調， 排程 CLI 呼叫、保存會議紀錄，並在使用者明確核准後執行專案。 跨 CLI 的交接走 .project-memory/ 與 Git。

Desktop app, remote bridge, phone app: three runtimes, one set of terminals

An Electron desktop app owns the CLI child processes. A LAN bridge inside its main process re-publishes those same terminals over HTTPS. An iPhone Home Screen web app attaches to them. Cowork coordinates meetings and approved work in the main process; official CLIs run the models.

Official CLIs own the agent runtime. The workbench provides editing, Git, terminals, shared memory and Cowork coordination, scheduling CLI calls and explicitly approved project work. Cross-CLI hand-off goes through .project-memory/ and Git.

系統全貌

三個執行環境、一條資料主幹。主行程是唯一擁有 pty 子行程與檔案系統存取權的地方； 桌面 renderer 透過 preload 這道唯一的縫隙跟它說話，手機透過 WebSocket。

The shape of it

Three runtimes, one spine. The main process is the only place that owns pty child processes and filesystem access; the desktop renderer talks to it through one preload seam, the phone over a WebSocket.

一條 pty，多個訂閱者

這是整個遠端控制能成立的那一個設計：pty 不綁死在某個 webContents 上。 它由主行程持有，誰想看就登記成訂閱者——桌面視窗是一個，手機是另一個。 因此手機不需要第二套 agent runtime，它看到的就是你電腦上那個終端本身。

One pty, many subscribers

This is the single design decision that makes remote control possible: a pty is not bound to one webContents. The main process owns it and anyone interested registers as a subscriber — the desktop window is one, the phone is another. So the phone needs no second agent runtime; what it shows is literally the terminal on your computer.

從輸出推導出來的三個訊號

  • 等你回覆（needsApproval）——shared/approvalDetect.ts 用一組字串樣式看輸出尾段 600 字。只在 false→true 的那一刻發事件，所以同一個提示不會連發推播；任何輸入進來就清掉，桌面與所有手機同時收卡片。
  • 執行中（busy）——最近 4 秒內還有輸出。由桌面判定，翻轉時才廣播一則 activity。不能讓手機拿自己的時鐘去比桌面寫的 lastOutputAt： 時鐘差一點就永遠顯示錯，而且 state 不是每次輸出都重送，會卡在舊值。
  • dev server port（devPort）——shared/portDetect.ts 看 scrollback 的尾段 4 KB， 不是看單一個 chunk：Vite 那行被切成兩次寫入時，只看 chunk 就抓不到。有了它手機才會出現「預覽」分頁。

Three signals derived from the output

  • Waiting for you (needsApproval) — shared/approvalDetect.ts runs a set of patterns over the last 600 characters. The event fires only on the false→true edge, so one prompt never produces a stream of pushes; any input clears it, and the desktop and every phone drop the card together.
  • Running (busy) — output within the last 4 seconds. Decided on the desktop, broadcast as one activity message on each flip. The phone must not compare its own clock against the desktop's lastOutputAt: a small clock skew makes it permanently wrong, and state is not re-sent on every chunk, so it would sit on a stale value.
  • Dev-server port (devPort) — shared/portDetect.ts reads the last 4 KB of scrollback rather than a single chunk: when Vite's banner arrives as two writes, a per-chunk match finds nothing. This is what makes the phone's Preview tab appear.

為什麼 iPhone 要另外安裝一張憑證

手機連的是 https://192.168.x.x:47600——一個私有 IP，沒有網域名稱。 公開的憑證頒發機構依規定不會、也不能為私有 IP 簽憑證（它們無法證明誰擁有 192.168.1.5）。 所以只剩兩條路：不要 HTTPS，或者用你自己這台電腦簽的憑證。

不要 HTTPS 這條走不通，因為 iOS 把這三件事綁在「可信任的 HTTPS」上：

  • 加入主畫面後當成真正的 App（standalone，沒有 Safari 的網址列）；
  • Service Worker——通知就是靠它收的；
  • Web Push——agent 等你回覆時那則通知。

而且「自簽憑證＋點仍要前往」也不算：那樣 Safari 會把這個 origin 標成憑證無效， 上面三個 API 照樣是關著的。所以必須是一張手機真的信任的憑證。

於是桌面自己當一張 CA：你在手機上安裝並開啟「完全信任」一次（這就是那個一次性步驟）， 之後每次區網 IP 變動，桌面就用同一張 CA 重簽 server 憑證——手機不必再裝任何東西。 一台電腦一張 CA，所以多台電腦就要各裝一次。

風險控管：這張 CA 帶 critical 的 X.509 Name Constraints，只准簽私有 IPv4 與 *.local——就算私鑰外洩，也簽不出能在你手機上冒充 google.com 的憑證。 私鑰以 OS 金鑰（Electron safeStorage）封裝；「重設憑證與所有裝置」會換一張新的 CA。 憑證在 SAN 不再涵蓋目前 IP、或離到期不到 30 天時重簽，而比對是逐項相等不是字串包含： IP Address:192.168.1.1 不可以被 …1.10 誤判成已涵蓋， 否則換 IP 後不重簽，手機就連不上。

Why the iPhone has to install a certificate

The phone connects to https://192.168.x.x:47600 — a private IP with no domain name. Public certificate authorities will not and cannot issue for a private IP (there is no way to prove who owns 192.168.1.5). That leaves two options: no HTTPS, or a certificate your own computer signs.

No HTTPS is not an option, because iOS gates three things on trusted HTTPS:

  • Behaving like a real app once added to the Home Screen (standalone, no Safari address bar);
  • Service workers — which is how the notification is received;
  • Web Push — the notification itself when an agent is waiting for you.

And a self-signed certificate you click through does not count either: Safari marks that origin as having an invalid certificate and those three APIs stay switched off. It has to be a certificate the phone actually trusts.

So the desktop becomes a small CA. You install it on the phone and turn on full trust once — that is the one-time step — and from then on the desktop re-signs the server certificate from that same CA whenever the LAN IP changes, with nothing to reinstall. One CA per computer, so several computers means installing one each.

Risk control: the CA carries critical X.509 Name Constraints permitting only private IPv4 ranges and *.local — even with the key, it cannot sign a certificate that impersonates google.com on your phone. Its private key is sealed with the OS keychain (Electron safeStorage), and "reset certificate and devices" generates a new CA. A certificate is re-issued when its SAN no longer covers the current IP or it is within 30 days of expiry, and the comparison is entry-by-entry equality rather than substring: IP Address:192.168.1.1 must not match …1.10, or the certificate is never renewed after an IP change and the phone can no longer connect.

  • Read — the xterm buffer reflowed for a phone: soft wraps joined, TUI borders dropped, blank runs collapsed.
  • Terminal — the real xterm. On entry it resizes the pty to the phone's width, so there is nothing to scroll sideways.
  • Preview — appears when the terminal printed a dev-server URL.

Answering

  • prompt.ts 把 CLI 的問題解析成選項，並標出 CLI 目前選中的那個。
  • 文字與 Enter 分兩次送：agent CLI 會把同一批到達的「文字＋換行」當成貼上。
  • 多行輸入用 bracketed paste 包起來。
  • prompt.ts parses the CLI's question into options and marks the one the CLI has selected.
  • Text and Enter are sent as two writes, because agent CLIs treat a same-tick "text + newline" as a paste.
  • Multi-line input is wrapped in bracketed paste.

為什麼終端要改 pty 的欄數，而不是縮字

桌面開的 session 是 120 欄。只縮字級的話，要塞進 370px 寬的手機得用 5px 以下的字， 而字級下限是 6px——所以畫面一定會超出去，只能左右拖，而且 6px 根本看不清。 真正能解的是欄數：進終端就把 pty resize 成手機放得下的寬度（字級回到 12–13px）， 離開時還給電腦。本來就放得下就不動，轉向或鍵盤收合後重算一次（250 ms 節流，避免連續 resize 洗 pty）。

三台電腦、一次一條連線、不重新載入

WebSocket 不受同源政策限制，所以 App 可以把連線指向你選的那台，切換就是換掉連線—— 不導覽、不重新載入，主畫面 App 也不會被踢出 standalone。 hosts.ts 在 localStorage 存最多三筆 { url, label } 與每台各自一個的 token； conn.ts 吃目標位址，不再假設 location.host。

桌面端為此只讓了兩步，都收得很窄：

  • 握手的 Origin 檢查：原本只收這台電腦自己的 App，現在也收「同一個 App 由區網私有位址提供」 （certs.ts · isAllowedOrigin）。公網 origin 與明文 http 仍然擋掉，而且過了這關也只是拿到一條連線， 5 秒內沒有有效 token 照樣斷。
  • 配對：跨 origin 對 /api/pair 發 fetch 會死在 CORS，所以配對也做成 WebSocket 訊息 （pairRequest），在尚未驗證的連線上處理——一次性配對碼、5 分鐘失效、錯 10 次作廢，條件完全沿用。

Why the terminal resizes the pty instead of shrinking the font

A desktop session is 120 columns. Shrinking only the font would need something under 5px to fit a 370px phone, and the floor is 6px — so the view overflows and can only be dragged sideways, at a size nobody can read. The thing that actually fits is the column count: entering the terminal resizes the pty to the phone's width (which puts the font back at 12–13px) and gives the size back to the computer on the way out. If it already fits, nothing is touched; after a rotation or the keyboard collapsing it recomputes once, throttled to 250 ms so a drag-resize doesn't flood the pty.

Three computers, one connection at a time, no reload

A WebSocket is not bound by the same-origin policy, so the app can point its connection at whichever computer you pick and switch by swapping the connection — no navigation, no reload, and the Home Screen app never leaves its standalone context. hosts.ts keeps up to three { url, label } entries and one device token per computer in localStorage; conn.ts takes the target as a base URL instead of assuming location.host.

Two things had to give way on the desktop side, both narrowly:

  • The handshake's origin check. It accepted only this computer's own app; it now also accepts the same app served from another private-LAN address (certs.ts · isAllowedOrigin). Public origins and plain HTTP stay rejected, and passing the check still only yields a socket that is dropped after five seconds without a valid token.
  • Pairing. A cross-origin fetch to /api/pair dies at CORS, so pairing is also a WebSocket message (pairRequest) handled on the unauthenticated socket — same single-use code, same 5-minute expiry, same 10-attempt lockout.
仍然綁在單一位址的事。Web Push 訂閱屬於建立它的那個 origin 的 Service Worker， 所以通知只會來自送來這個 App 的那台電腦；其他台在 App 開著時是完全可控的。 另外每台電腦簽自己的憑證，手機要各裝一次——連不到時配對畫面會直接給你那台的憑證安裝頁連結。 What is still tied to one address. A Web Push subscription belongs to the origin whose service worker created it, so notifications arrive only from the computer that serves the app; the others are fully controllable while you have the app open. Each computer also signs its own certificate, so the phone installs each CA once — the pairing screen links straight to that computer's certificate page when it cannot reach it.

預覽：為什麼需要一個代理

三件事同時擋住最直覺的做法。

  1. 手機的 localhost 是手機自己，不是你的電腦。
  2. dev server 多半只綁 127.0.0.1，區網連不到。
  3. https 頁面不能框住 http 頁面（mixed content）。

所以橋接層自己代理：用它自己的 origin（port + 2），這樣被預覽頁面裡那些 /assets/… 根目錄相對路徑才會自然解對，不必改寫任何 HTML；HMR 的 WebSocket 一併轉發， 否則 Vite 會一直重連並蓋上錯誤畫面。

為什麼不是掛在 PWA 那台的 /preview/<port>/ 路徑下： 被預覽頁面的 /assets/x.js 會跑回橋接層的根目錄，和 App 自己的檔案撞在一起。 給它自己一個 origin，相對路徑就對了。

Preview, and why it needs a proxy

Three things block the obvious approach at once.

  1. The phone's localhost is the phone, not your computer.
  2. A dev server usually binds 127.0.0.1 only, so the LAN cannot reach it.
  3. An https page cannot frame an http one (mixed content).

So the bridge proxies it on its own origin (port + 2), which is what makes the previewed page's root-relative /assets/… requests resolve correctly without rewriting any HTML. The HMR WebSocket is forwarded too, otherwise Vite reconnects forever and paints an error overlay.

Why not mount it under /preview/<port>/ on the app's own origin: the previewed page's /assets/x.js would resolve to the bridge's root and collide with the app's own files. Giving it a separate origin makes relative paths correct by construction.

四條端到端流程

這幾條值得知道，因為它們把系統裡每一道邊界都走過一次。

agent 停下來問你，你在沙發上回答

  1. pty.ts一段 CLI 輸出進來。進 scrollback、送給每個訂閱者，並觸發 looksLikeApprovalPrompt。
  2. server.tsapproval 事件把去掉 ANSI 的尾段廣播給連線中的手機，並對「有訂閱但不在前景」的裝置送 Web Push。
  3. remote-sw.js顯示通知。點下去開到 /#s=<session>。
  4. TerminalViewprompt.ts 把問題做成按鈕，一下 input 送出那個選項的鍵。
  5. pty.ts鍵寫進子行程。任何輸入都會清掉 needsApproval，桌面與每支手機同時把卡片收掉。

在一個還沒開的工作區裡開 agent

  1. Home在「其他工作區」點一個 → openWorkspace。
  2. server.ts只接受桌面自己最近清單裡的路徑，然後開啟或聚焦那個專案視窗並重播 state。
  3. Home看到新視窗出現，自動為它打開「新增終端」。
  4. server.tsspawn 把 launcherKey 對照該工作區的允許清單，然後呼叫桌面在用的同一個 spawnPty。
  5. main通知桌面視窗為同一個 pty 開分頁——等它的 renderer 載完才送，所以你回到電腦前 agent 就在那裡。

在手機上看成品

  1. pty.tsdetectDevPort 讀輸出尾段（不是單一 chunk，所以網址被切成兩次寫入也抓得到），把 port 記在 session 上。
  2. TerminalView預覽分頁出現，點下去送 preview。
  3. PreviewProxy發一張一次性 ticket，回 https://<手機連進來的位址>:47602/__aw?t=…。
  4. iframe載入它，ticket 換成 HttpOnly cookie 並轉到 /。
  5. PreviewProxy把每個請求轉給 127.0.0.1:<port>，拿掉 X-Frame-Options 讓 App 框得住，並轉發 HMR 的連線。

切到另一台電腦

  1. Home點標題的下拉，選另一台（或在設定裡用區網位址新增一台）。
  2. hosts.ts記下「現在連哪台」，取出那台的 token。沒有 token 就先進配對畫面。
  3. conn.ts舊連線關掉，對新位址開一條 wss。整個畫面不重新載入。
  4. server.ts握手時認得這是「同一個 App 在區網另一個位址」，接受後仍要求 5 秒內送有效 token。
  5. Home收到 authed 與 state，把清單裡那台的名字換成電腦自己報的主機名。

Four flows end to end

These are the ones worth knowing, because they cross every boundary in the system.

An agent stops to ask — you answer from the sofa

  1. pty.tsA chunk of CLI output arrives. It lands in the scrollback, goes to every subscriber, and trips looksLikeApprovalPrompt.
  2. server.tsThe approval event broadcasts the ANSI-stripped tail to connected phones and sends a Web Push to devices that are subscribed but not in the foreground.
  3. remote-sw.jsShows the notification. Tapping it opens the app at /#s=<session>.
  4. TerminalViewprompt.ts turns the question into buttons; one tap sends input with that option's key.
  5. pty.tsThe key is written to the child process. Any input clears needsApproval, so the desktop and every phone drop the card together.

Starting an agent in a workspace that isn't even open

  1. HomeTaps one under Other Workspaces → openWorkspace.
  2. server.tsAccepts the path only if it is in the computer's own recent list, then opens or focuses that project window and re-broadcasts state.
  3. HomeSees the new window arrive and opens New Terminal for it automatically.
  4. server.tsspawn resolves the launcher key against that workspace's allow-listed launchers, then calls the same spawnPty the desktop uses.
  5. mainTells the desktop window to open a tab on the same pty — deferred until its renderer has loaded — so the agent is in front of you when you get back.

Checking the build on your phone

  1. pty.tsdetectDevPort reads the output tail (not a single chunk, so a URL split across writes still resolves) and records the port on the session.
  2. TerminalViewThe Preview tab appears; tapping it sends preview.
  3. PreviewProxyIssues a single-use ticket and replies with https://<the address the phone used>:47602/__aw?t=….
  4. iframeLoads it; the ticket is exchanged for an HttpOnly cookie and redirects to /.
  5. PreviewProxyForwards each request to 127.0.0.1:<port>, strips X-Frame-Options so the app can frame it, and relays the HMR socket.

Switching to another computer

  1. HomeTaps the title's dropdown and picks another one (or adds one by LAN address in Settings).
  2. hosts.tsRecords which computer is active and reads that computer's token. No token means the pairing screen first.
  3. conn.tsCloses the old connection and opens a wss to the new address. The page never reloads.
  4. server.tsRecognises the handshake as the same app from another private-LAN address, and still demands a valid token within five seconds.
  5. HomeOn authed and state, relabels that entry with the host name the computer reports.

信任邊界

誰能讓這個 App 做事，以及什麼在擋。有意思的不是網路那幾道——是那些跟著 repo 一起進來的檔案。

邊界另一邊是誰什麼在擋
區網 同一個 Wi-Fi 上任何能打到 47600–47602 的東西 非私有位址在 TCP 層就被斷。配對是唯一不需驗證的入口：8 字元、31 字母表（去掉易混淆的 0/O、1/I/L）、一次性、5 分鐘失效、錯 10 次作廢、常數時間比對。
已配對的手機 完成配對的裝置 設計上它就有完整終端控制權——能打字、能開能殺 agent、能切 Bypass 模式（開啟要確認，桌面會跳通知）。256-bit token 只存 SHA-256，撤銷裝置立即斷線。
專案 repo 你打開的任何專案——clone 的、下載的、別人傳給你的 repo 帶的檔案一律當不受信任輸入：agents/*.yaml 的 launcher 只能指名已知的 CLI，也不准設 NODE_OPTIONS／PATH 這類會在別人行程裡插程式碼的變數；.workbench/settings.json 不能改 CLI 解析到哪個執行檔、不能打開 Bypass；.workbench/extensions.yaml 的 id 有格式檢查、skill 路徑必須留在工作區內，所以同步不會寫到它宣稱的目錄之外。
被渲染的內容 工作區裡的 Markdown、圖表、文件 renderer 握著 window.api，所以那裡的 HTML 注入等於程式執行：Mermaid 跑在 securityLevel: 'strict'、HTML 預覽的 iframe 沒有 allow-scripts、Markdown 連結過濾 scheme、<webview> 的權限由 main 釘死而不是由標籤屬性決定。
Agent CLI 子行程本身 它以你的身分、你的 shell、你的檔案在跑——那正是這個產品的用途。Bypass 模式是唯一會關掉它自己審批的開關，預設關閉、每台機器各自設定，開著時桌面與手機都看得到。
網際網路 Apple 推播服務、GitHub releases、各廠商的安裝腳本 推播內容在離開前就已為手機加密（RFC 8291），而且只接受已知的推播主機當端點。更新檢查與 CLI 安裝都由使用者觸發，走各廠商自己的 HTTPS 端點。

輸入法與終端的那道縫

imeGuard.ts 存在的原因：組字進行中、還沒送出的字是放在 xterm 隱藏的 <textarea> 裡。 程式去呼叫 focus()（或 resize 造成重繪）會讓 Chromium 中止這次組字，而被中止的內容會留在 textarea 裡沒被清掉。 xterm 判斷「輸入法這次送了什麼」用的是 textarea 內容的前後差異，所以下一個組字鍵進來時，殘留那段會被當成新輸入再送一次—— 看起來就是「打到一半的字又被貼上一次」。所以組字中一律不搶 focus、不改尺寸；真人點擊不受影響。

The IME seam in the terminal

Why imeGuard.ts exists: while an IME composition is in progress, the not-yet-committed text lives in xterm's hidden <textarea>. A programmatic focus() (or a resize that forces a redraw) makes Chromium abort the composition, and the aborted text stays in the textarea uncleared. xterm decides what the IME just produced by diffing the textarea's contents, so the next composition key re-sends that leftover as new input — which looks exactly like the half-typed text being pasted again. So nothing steals focus or changes size while composing; a real click is unaffected.

  • 兩個 renderer entry，一次 build：src/renderer/index.html（桌面）與 src/renderer/remote.html（手機）由同一個 Vite 設定產出，橋接層從 out/renderer 提供手機那份。開發時要先跑一次 npm run build，npm run dev 才有手機端可以測。

  • 更新：預設不自動下載。安裝版走 electron-updater，失敗或免安裝版就退回 GitHub Releases API 查詢；「是不是安裝版」用 exe 旁邊有沒有 NSIS 的解除安裝程式判斷，不能用保護目錄判斷（那對 exe 目錄恆為真，可攜版會被誤判成安裝版）。

Build and packaging

  • Two renderer entries, one build. src/renderer/index.html (desktop) and src/renderer/remote.html (phone) come out of one Vite config, and the bridge serves the phone one from out/renderer. In development run npm run build once so npm run dev has a phone client to serve.
  • Native dependencies. @lydell/node-pty ships a .node binary (conpty) that must be unpacked from the asar, or terminals don't start at all in a packaged build. Both it and simple-git are kept out of the bundle by externalizeDepsPlugin.
  • Targets. Windows NSIS (not one-click, installation directory changeable, per-user), macOS dmg, Linux AppImage; publishing goes through the GitHub provider.
  • Updates. No automatic download by default. Installed builds use electron-updater, with a GitHub Releases API fallback for portable builds or when that fails. "Is this an installed build" is decided by whether an NSIS uninstaller sits next to the exe — not by a protected-directory check, which is always true for the exe's own directory and would misread a portable copy as installed.
  • Self-checks. npx tsx scripts/check-remote.mts verifies the CA's name constraints (by actually completing a TLS handshake and confirming a certificate impersonating www.google.com is rejected), Web Push decryption, VAPID signatures, the preview ticket/cookie flow, and the WebSocket origin rule; three more cover the computer registry, port detection and usage parsing.

已知取捨

這些是刻意留著的，不是忘了。寫在這裡，下次有人想動的時候才知道當初為什麼。

  • 推播只來自一台：Web Push 訂閱綁 origin，所以多電腦切換時只有「送來這個 App 的那台」會推。要讓每台都能推，得為每台註冊不同 scope 的 Service Worker，並把 VAPID 公鑰與訂閱改走 WebSocket——還沒做。
  • 預覽的 frame-src 放到 https:：預覽可能在你選的另一台電腦上，CSP 沒辦法表達「私有網段」，而這台電腦也不知道你記了哪幾台。被框住的頁面本來就碰不到 App 的東西。
  • 桌面 renderer 的 CSP 含 unsafe-inline 與 unsafe-eval：Monaco 需要。這也是為什麼「被渲染的內容」那道邊界要守得特別緊——那裡的 HTML 注入等於程式執行。
  • Bypass 模式：開著時之後啟動的 agent 不再詢問。這是使用者明確要的功能，所以保留，但預設關閉、開啟要確認、桌面跳通知、手機首頁常駐警示。
  • 沒有程式碼簽章：electron-updater 在沒有 publisherName 時會跳過安裝檔的簽章驗證，更新的完整性只靠對 GitHub 的 TLS。install.ps1 也只比對檔案大小，沒有比對雜湊。
  • 審批偵測是純文字啟發式：各家 CLI 換個提示字串就會失準。升級路徑是哪家 CLI 走結構化輸出（如 stream-json）就改那家，不必動其他家。

Known trade-offs

These are deliberate, not forgotten. Written down so the next person to touch them knows why.

  • Push comes from one computer. A Web Push subscription is tied to an origin, so with several computers only the one that served the app can push. Per-computer push would need a separate service-worker scope per computer plus moving the VAPID key and the subscription onto the WebSocket — not done.
  • The preview's frame-src is https:. A preview may live on whichever computer you picked, CSP cannot express "private LAN", and this computer doesn't know which computers you remembered. The framed page cannot touch the app regardless.
  • The desktop renderer's CSP allows unsafe-inline and unsafe-eval. Monaco needs them. It is also why the "rendered content" boundary is guarded so tightly — HTML injection there is code execution.
  • Bypass Mode. While on, agents started from then on stop asking. It is a feature people explicitly want, so it stays — off by default, confirmed on enable, with a desktop notification and a standing warning on the phone's home screen.
  • No code signing. Without a publisherName, electron-updater skips signature validation of the downloaded installer, so update integrity rests on TLS to GitHub alone. install.ps1 likewise only checks the file size, not a hash.
  • Approval detection is a text heuristic. Any CLI that rewrites its prompt breaks it. The upgrade path is per vendor: when one ships structured output (such as stream-json), switch that one over without touching the others.
